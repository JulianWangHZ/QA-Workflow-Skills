# qa-risk — 風險分析

回答一個問題：**這次變更最可能在哪裡出錯，出錯的代價多大？**
風險分析是讀程式碼後的因果推理，不是關鍵字比對。

`qa` = `node "<本 skill 目錄>/../qa-workflow/bin/qa.mjs"`

- 讀取：`qa path context`，以及 context 列出的來源與變更檔案
- 寫入：`qa path risks`（格式：`../qa-workflow/schemas/risks.schema.json`）

## 流程

### 1. 讀程式碼

把範圍內的核心實作讀完：入口（路由、controller、頁面）→ 業務邏輯 → 資料存取 → 對外呼叫。
記下每個「如果這裡錯了會怎樣」的點。

### 2. 用 10 個面向逐一檢視

| 面向 | 問自己 |
|---|---|
| 資料正確性 | 計算、精度、單位、時區、四捨五入是否一致？ |
| 狀態與流程 | 狀態能不能被跳過、倒退、重入？中途失敗會停在哪個狀態？ |
| 權限與隔離 | 誰能呼叫？有沒有檢查資料擁有者？未登入時怎麼處理？ |
| 併發與冪等 | 重複請求或同時請求會不會造成重複扣款、超賣、計數錯誤？ |
| 外部依賴 | 第三方失敗、逾時、回呼延遲時，資料是否一致？有沒有重試？ |
| 資料生命週期 | 刪除、軟刪除、遷移、快取失效後，引用端是否正確？ |
| 輸入邊界 | 空值、極值、格式錯誤、特殊字元有沒有被處理？ |
| 相容與回歸 | 既有呼叫端、API 契約、舊資料、其他共用這段程式的功能會不會壞？ |
| 錯誤處理 | 錯誤是否被吞掉？使用者看到什麼？會不會洩漏內部資訊？ |
| 安全 | 注入、XSS、敏感資料外洩、未授權存取？ |

### 3. 分級

| 等級 | 定義 |
|---|---|
| P0 | 金錢或資料損失、資料不一致、越權、安全漏洞、主流程完全無法使用 |
| P1 | 核心業務規則錯誤、重要功能退化、影響大量使用者 |
| P2 | 邊界與例外處理不當、非主要流程錯誤、有替代方式 |
| P3 | 顯示、文案、體驗細節 |

- 分級看**出錯的代價**，不看發生機率。機率另外寫在 `likelihood`。
- 不確定時選較高的等級，並在 `notes` 說明。

### 4. 寫出風險

每個風險包含：
- `id`：`R-<數字>`
- `title`：一句話描述會出什麼錯
- `level`
- `area`：功能區塊
- `impact`：對使用者或業務的具體後果
- `evidence`：至少一條依據，例如 `src/order/service.ts:88 扣庫存前未檢查數量`，或需求段落

沒有依據的推測可以列，但必須在 `evidence` 寫明「推測：...」並降低等級，不要當成確定事實。

### 5. 驗證並回報

1. 執行 `qa validate risks`。
2. 回報調度者，內容包含：
   - 各等級數量
   - 前 3 個最高風險

## 規則

- 找不到任何風險時也要寫出 `risks: []`，並在回報中說明為什麼認為風險很低。
- 不因為「應該有測試覆蓋」就降低等級。測試是否足夠，由後面的階段驗證。
