# BDD 撰寫規範

feature 是**用例本身**。同一份檔案要同時讓三種讀者滿意：

| 讀者 | 需求 |
|---|---|
| PM／CS | 在審閱頁的「驗收清單」讀白話內容，對照 AC |
| QA | 直接轉成自動化測試 |
| CLI | 解析結構與 tag，做覆蓋檢查 |

## 語言：英文關鍵字、中文內容

- 結構關鍵字一律英文：`Feature`、`Background`、`Scenario`、`Given`、`When`、`Then`、`And`、`But`。
- 描述、步驟、tag 用中文（或團隊的工作語言）。
- **不要加 `# language:`**，也不要用中文關鍵字（功能、場景、假如、當、那麼…）。CLI 會擋下，大多數 BDD 框架也會解析失敗。
- 具體資料用雙引號包起來，例如 `"amy@example.com"`、`"NT$350"`、`"帳號已鎖定"`。

## 檔案結構

```gherkin
# 頁面 code 路徑：src/checkout/CheckoutPage.tsx
# 註：付款流程在 payment.feature，本檔只涵蓋下單前的檢查
@會員
Feature: 購物車結帳
  作為一個會員
  我想要把購物車中的商品結帳
  以便收到我買的東西

  Background:
    Given 我已登入會員帳號 "amy@example.com"

  # ############################################
  # 庫存檢查
  # ############################################
  @結帳頁面 @smoke @regression @auto @庫存充足
  Scenario: 庫存充足時可以下單
    Given "馬克杯" 庫存為 "3"
    When 我購買 "1" 個 "馬克杯"
    Then 訂單成立
    And 庫存變為 "2"

  @結帳頁面 @regression @auto @庫存不足
  Scenario: 庫存不足時無法下單
    Given "馬克杯" 庫存為 "0"
    When 我購買 "1" 個 "馬克杯"
    Then 系統顯示 "商品庫存不足"
    And 不會建立訂單

  # ############################################
  # 數量上限
  # ############################################
  @結帳頁面 @regression @auto @邊界 @數量剛好上限
  Scenario: 單筆購買剛好 10 個可以下單
    When 我購買 "10" 個 "馬克杯"
    Then 訂單成立
```

| 元素 | 規則 |
|---|---|
| 檔頭註解 | `# 頁面 code 路徑：` 填主要實作檔，找不到就填模組目錄；後台或沒有前端時可省略。`# 註：` 記錄與其他 feature 的關係，可多行 |
| Feature 層 tag | 同一個 feature 中有多種角色需要區分時，才加角色 tag（例如 `@店員` `@店長`）。只有一種角色就省略 |
| Feature 說明 | 必填三行：`作為一個…`／`我想要…`／`以便…`。審閱頁會把它放在驗收清單最上方，讓 PM 對 AC |
| Background | 只放**所有** Scenario 都需要的前置條件 |
| 段落分隔 | 用 `# ####…` 包住段落名稱，把 Scenario 依業務功能分組。驗收清單會照這個分組 |
| Scenario 標題 | 業務行為 + 條件，例如「庫存不足時無法下單」。**所有 feature 中必須唯一**，因為要用標題對應編號與自動化測試 |
| Scenario Outline | **不使用**。每組資料寫成獨立的 Scenario，讓每個情境都能單獨驗收與追蹤 |

## 宣告式：寫意圖，不寫操作

步驟描述使用者**要做什麼**，不描述**怎麼點**。

| | 寫法 |
|---|---|
| ✅ 宣告式 | `When 我預約 "2026/07/01 10:00" 的剪髮服務` |
| ❌ 命令式 | `When 我點選日期 "2026/07/01"`、`And 我點選時段 "10:00"`、`And 我按下確認` |

- 一個業務動作一個步驟。如果需要好幾個命令式步驟才說得清楚，代表 step definition 應該封裝成一個業務方法，而不是在 feature 中展開。
- 同一份 feature 中不要混用宣告式與命令式。
- 從使用者角度撰寫。不寫「直接呼叫 API 繞過前端」這類開發者視角的情境；後端的防護由單元或整合測試處理。
- 每個 Scenario 都能獨立執行，不依賴其他 Scenario 的結果。
- 每個 Scenario 都必須有來源：需求、測試矩陣或狀態機。不憑空編造情境。

## Tag：三個軸，加上描述

每個 Scenario 上的 tag 分成四類，**彼此獨立、不能互相取代**：

| 類別 | 回答的問題 | Tag | 規則 |
|---|---|---|---|
| 套件 | 什麼時候跑？ | `@regression`、`@smoke` | **每個 Scenario 都要有 `@regression`**（正向、負向都算）。核心成功流程再加 `@smoke`，每個 feature 通常 1–3 個。`@smoke` 一定也要有 `@regression` |
| 執行 | 誰來跑？ | `@auto` | 能用程式執行**而且**能用程式驗證，就標 `@auto`。沒有 `@auto` 就是人工驗收，原因寫在 `# 註：` |
| 性質 | 是不是極端情境？ | `@邊界` | 只標真正的極端：臨界值（剛好 24 小時前）、資源耗盡（額度用完）、競態（同時搶最後一個名額）、故障（服務錯誤、斷線） |
| 描述 | 測的是什麼？ | 中文 tag | 至少一個頁面 tag（例如 `@結帳頁面`）與一個情境條件 tag（例如 `@庫存不足`），4–8 字的名詞片語 |

判斷補充：
- 功能尚未實作，**不是**拿掉 `@auto` 的理由。依「本質上能不能用程式驗證」判斷，並在 `# 註：` 記下待確認的地方。
- 真實簡訊、人工審核、視覺比對、多語系切換這類，才一開始就不標 `@auto`。
- 一般的無效輸入、權限不足、查無資料，是**負向**，不是 `@邊界`。
- 測資難建是執行成本（`@auto` 軸），不是 `@邊界` 的理由，也不是拿掉 `@regression` 的理由。

**不要放進 tag**：
- 情境編號、優先級、風險編號（例如 `@TC-3`、`@P0`、`@R-1`）
- 版本號
- 把 Scenario 標題當成 tag
- tag 中含空白：`@24 小時前` ❌ → `@24小時前` ✅

## 編號、優先級與風險：寫在 design.json

每個 Scenario 都要在 `design.json` 的 `scenarios` 有一筆，用**檔案與標題**對應：

```json
{ "id": "TC-2", "file": "checkout.feature", "title": "庫存不足時無法下單",
  "priority": "P0", "riskIds": ["R-1"], "type": "negative" }
```

| 欄位 | 說明 |
|---|---|
| `id` | `TC-<數字>`，依序編號 |
| `file` | 相對於 `design/features/` 的路徑 |
| `title` | 與 Scenario 標題完全相同 |
| `priority` | P0–P3 |
| `riskIds` | 驗證的風險；覆蓋率只看這個欄位 |
| `type` | positive、negative、boundary、error、permission、state、concurrency、integration、ui、performance、security、regression 其中之一 |

CLI 會檢查兩邊是否一一對應：
- feature 中有、索引中沒有的 Scenario，會被擋下。
- 索引中有、但 feature 中找不到的，也會被擋下。

這樣 feature 保持乾淨，可以直接放進專案；追蹤資訊集中在一個地方。
