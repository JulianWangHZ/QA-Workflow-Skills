# PM 驗收清單（`design.json` → `pmAcceptance`）

從全部情境挑出給 PM／RD 對齊的子集，審閱頁會放在「PM 驗收清單」分頁，原型也會預設只列這些情境。

**定位**：PM 清單只用來對齊 user story。測試範圍、自動化與 QA 執行一律以全部情境（QA 驗收清單）為準，PM 清單不影響任何後續階段。

## 挑選規則

目標**約 10 條，上限 12**（CLI 會擋超過 12）：符合下表「收」的不到 10 條就照實際數量，不硬湊。

| 收 | 不收 |
|---|---|
| 每個 user story 的主要正向（通常是 `@smoke`） | 元件可見、按鈕可點、欄位顯示、文案、樣式 |
| 主要負向：業務規則擋下、權限或資格不符 | 同一規則的多種無效輸入變形（取一條代表） |
| P0／P1 風險對應的情境 | 基礎設施錯誤：網路不穩、5xx、逾時（除非本次範圍就是處理它） |
| 需要 PM 決定產品怎麼回應的異常：流程中途出錯、外部服務失敗、操作中資料被改動 | 與 PM 無關的技術性錯誤處理（重試次數、log、錯誤碼） |
| 少數高價值邊界：使用者實際會遇到且影響金流、名額、資料正確性 | 純技術邊界（字數上限、連點），除非評估後確實是高風險 |

- 一條可涵蓋多個情境：主要情境填 `caseId`，其餘填 `relatedCaseIds`（例：同一結果的正向變形）。
- P0／P1 風險已被其他 PM 情境間接驗到時，不另收只檢查畫面呈現的情境；在 `rationale` 寫明由哪條涵蓋。
- 超過 12 條：先合併同規則情境，再刪優先度低的邊界；不得刪主要正向、P0／P1 風險與需 PM 決定的異常。

## 格式

```json
"pmAcceptance": {
  "items": [
    { "caseId": "TC-3", "title": "審核失敗時店長看得到原因", "summary": "平台以原因駁回一張照片",
      "expected": "照片出現在「審核失敗」分組，可查看駁回原因", "relatedCaseIds": ["TC-4"] }
  ],
  "openQuestions": ["iOS 前景時審核推播要不要跳橫幅？"],
  "rationale": "收：上傳→審核→上線／失敗主流程、配額（R-1）；未收：頁籤分組與檢視器等畫面細節"
}
```

- `caseId` 沿用情境編號，PM 卡片與 QA 清單、原型的編號一致；類型與優先級直接取該情境的 `type`、`priority`。
- 讀者是 PM／RD：`title`、`summary`、`expected` 寫業務結果，不寫 UI 操作與技術詞。
- `openQuestions`：只放 PM 能回答、會影響預期結果的業務問題，用白話改寫；純技術待查項留在 `design.json` 的 `openQuestions`。
